rules_helm

rules_helm

Bazel rules for producing helm charts

Setup MODULE.bazel

rules_helm is published to the Bazel Central Registry:

bazel_dep(name = "rules_helm", version = "{version}")

Charts that bundle container images use one of the companion modules instead. See Container images.

Run as a tool

bazel run @helm//:helm -- ...

A matching kubectl is available for inspecting the cluster after a deploy. See Kubernetes tools for setup.

bazel run @kubectl//:kubectl -- ...

Use in a genrule

genrule(
    name = "genrule",
    srcs = [":chart"],
    outs = ["template.yaml"],
    cmd = "$(HELM_BIN) template my-chart $(execpath :chart) > $@",
    toolchains = ["@rules_helm//helm:current_toolchain"],
)

Environment variables

RULES_HELM_IMAGE_PUSH_CONCURRENCY

How many of a chart's bundled image pushers run at once. Defaults to 4, and applies to helm_push, helm_push_images, helm_install and helm_upgrade.

Each image is pushed by its own process, which authenticates with the registry before it looks at anything, so a chart with many images spends most of the push waiting rather than transferring. Running the pushers concurrently keeps that cost from scaling with the image count.

Set it to 1 to push one image at a time. A serial run also streams each pusher's output live on its own streams, instead of capturing it and replaying it as a block once the pusher exits, which makes a single failing push easier to follow.

Values that are not a positive integer are ignored with a warning.

Helm images

HelmImageInfo is the contract between rules_helm and the rules that build container images. helm_package.images accepts any target that provides it.

rules_helm provides it itself for oci_push, image_push and image_import targets by recognising them by shape. The companion modules provide it from the image rules' own providers instead:

  • rules_helm_img: helm_img_image
  • rules_helm_oci: helm_oci_image

helm_image is the reference implementation for anything else.

A container image a helm chart refers to.

helm_import_repository

load("@rules_helm//helm:helm_import.bzl", "helm_import_repository")

helm_import_repository(name, chart_name, repository, sha256, url, version)

A rule for fetching external Helm charts from an arbitrary URL or repository.

With bzlmod, the helm_charts extension in @rules_helm//helm:extensions.bzl fetches oci:// charts with this rule and stores the digest it looks up in MODULE.bazel.lock.

The repository exposes the chart as a helm_import target. The target takes its name and version from the Chart.yaml of the chart, not from the file name or the tag of the url. A chart fetched from oci://.../cert-manager:1.19.4 has the version v1.19.4 if its Chart.yaml says so, and helm push uses that version as the tag. The name can use letters, digits, -, . and _, and the version the same characters and +. Neither the chart name nor the repository name can be license or package_metadata. The target is aliased to the repository name, so @<name> resolves to it, unless the chart has the same name as the repository. The repository also describes the chart for supply-chain tooling built on package_metadata:

  • //:package_metadata identifies the chart by purl, pkg:oci/... for a chart from an OCI registry and pkg:generic/... with the download_url and sha256 checksum otherwise. It is the default_package_metadata of the repository.
  • //:license declares the chart's license, the SPDX identifier named by the licenses or artifacthub.io/license annotation of Chart.yaml or recognized in the LICENSE file shipped with the chart. It is NOASSERTION when neither is available. The license file, if any, is kept next to the chart as the license text.

ATTRIBUTES

NameDescriptionTypeMandatoryDefault
nameA unique name for this repository.Namerequired
chart_nameChart name to import. Must be set if repository is specifiedStringoptional""
repositoryChart repository url where to locate the requested chart. Mutually exclusive with url.Stringoptional""
sha256The expected SHA-256 hash of the chart imported. For an oci:// url, a chart already in the repository cache is then fetched without any request to the registry.Stringoptional""
urlThe url where a chart can be directly downloaded. Mutually exclusive with chart_name, repository, and versionStringoptional""
versionSpecify a version constraint for the chart version to use. Must be set if repository is specified.Stringoptional""

helm_oci_digest

load("@rules_helm//helm:helm_oci_digest.bzl", "helm_oci_digest")

helm_oci_digest(name, chart, registry_url, registry_url_file)

Compute the OCI manifest digest for a Helm chart at build time.

This rule constructs the OCI manifest that helm push (Helm v4) would create and computes its sha256 digest. The creation annotation comes from the chart's own org.opencontainers.image.created annotation, resolved by the stamping pass, and is formatted in UTC to match the push side.

The digest file contains a single line: sha256:<hex>.

The manifest and config blobs are also emitted, so a pusher that uploads them itself can PUT the exact bytes this digest was computed over. The manifest annotations and the tag are emitted for a pusher that builds the manifest itself. With registry_url or registry_url_file, so is the repository helm push would push to. None of these are in the default outputs; read them off HelmOCIDigestInfo or its output groups.

ATTRIBUTES

NameDescriptionTypeMandatoryDefault
nameA unique name for this target.Namerequired
chartA helm_chart target providing HelmPackageInfo.Labelrequired
registry_urlThe registry URL given to helm push, for example oci://registry.example.com/charts. Sets HelmOCIDigestInfo.repository. Only oci:// URLs are accepted; any other scheme fails the target, digest included. Mutually exclusive with registry_url_file.Stringoptional""
registry_url_fileA file containing the registry URL given to helm push. Sets HelmOCIDigestInfo.repository. As with registry_url, only oci:// URLs are accepted. Mutually exclusive with registry_url.LabeloptionalNone

An example of defining and using host tools:

helm.host_tools(name = "helm")

plugin

An extension tag for declaring Helm plugins.

Plugins are downloaded per-platform and made available to helm.toolchain() tags that reference them by name. Only platforms listed in integrity (and url_templates) will receive the plugin.

An example of declaring the helm-diff plugin and wiring it into a named toolchain:

helm = use_extension("@rules_helm//helm:extensions.bzl", "helm")
helm.host_tools()
helm.plugin(
    name = "diff",
    version = "3.15.5",
    strip_prefix = "diff",
    url_templates = {
        "darwin-arm64": ["https://github.com/databus23/helm-diff/releases/download/v{version}/helm-diff-macos-arm64.tgz"],
        "linux-amd64": ["https://github.com/databus23/helm-diff/releases/download/v{version}/helm-diff-linux-amd64.tgz"],
    },
    integrity = {
        "darwin-arm64": "sha256-KJmZ7wY3gAcWFzK5R9+TfQlaRfEXzJ7hDNRC8NgIDog=",
        "linux-amd64": "sha256-ToJjCrKyMxfAOeezsWYF95qKwPPSKHPg1G6pzZgN2o4=",
    },
)
helm.toolchain(
    name = "with_diff",
    plugins = ["diff"],
)
use_repo(helm, "helm", "helm_toolchains", "with_diff_toolchains")
register_toolchains("@helm_toolchains//:all")

toolchain

Define a named set of helm toolchains with specific plugins.

Creates an independent hub repository @{name}_toolchains containing toolchains for the default helm version with the specified plugins baked in. Only platforms where all referenced plugins are available will have toolchains generated.

The hub is not registered automatically — call register_toolchains explicitly, or use a Starlark transition to override toolchain resolution.

helm = use_extension("@rules_helm//helm:extensions.bzl", "helm")
helm.plugin(name = "diff", ...)
helm.toolchain(
    name = "with_diff",
    plugins = ["diff"],
)
use_repo(helm, "with_diff_toolchains")
register_toolchains("@with_diff_toolchains//:all")

helm_charts

helm_charts = use_extension("@rules_helm//helm:extensions.bzl", "helm_charts")
helm_charts.chart(name, sha256, url)

Module extension for fetching Helm charts from OCI registries.

Charts live in their own extension, so an unreachable registry does not stop the helm extension from resolving toolchains. All tags are resolved in one evaluation, so a lookup that fails (an unknown version or an unreachable registry) fails every repository from this extension. Set sha256 to skip the lookup. A command that loads a target from one of these repositories, such as bazel query, needs every lookup that has no stored fact. Tags from every module are used, so repository names must be unique across modules.

TAG CLASSES

chart

Fetch a Helm chart from an OCI registry with helm_import_repository.

The repository holds a helm_import target named after the name in the Chart.yaml of the chart, which is normally the last path segment of url without the version. Refer to it as @<name>//:<chart>. The shorthand @<name> is an alias of it, but only when the name in use_repo is the same as the tag name, because Bazel reads @x as @x//:x. Neither name nor the chart can be called license or package_metadata.

If sha256 is unset, the extension reads the digest of the chart package from the registry manifest, and trusts the registry for it on first use. On Bazel 8.5 and newer the digest is stored as a fact in MODULE.bazel.lock, keyed by url, so later evaluations make no registry request for it. Older Bazel versions record the digest in the lockfile as part of the repository. Without a lockfile, the digest is looked up whenever the extension is evaluated, and a version tag that the registry moves gives a different chart. Set sha256 to pin the digest in MODULE.bazel.

Each lookup is a token request and a manifest download, and the lookups run one after another. While a lookup is needed, an unreachable registry fails the evaluation, and so fails every target that depends on a repository from this extension. This applies whenever no stored fact exists: with the lockfile off, on the first evaluation, or after you delete the fact. A tag with sha256 makes no lookup while the extension evaluates. Fetching the chart can still contact the registry, unless the chart is in the repository cache.

A stored digest is not checked against the registry. If the registry replaces the chart behind a version tag, the fetch fails with a checksum mismatch. Delete the entry for url from the facts section of MODULE.bazel.lock to look the digest up again.

helm_charts = use_extension("@rules_helm//helm:extensions.bzl", "helm_charts")
helm_charts.chart(
    name = "karpenter",
    url = "oci://public.ecr.aws/karpenter/karpenter:1.9.0",
)
use_repo(helm_charts, "karpenter")

# Then you can use @karpenter//:karpenter as a dependency in your BUILD files

Container images

A chart's images attribute accepts push targets from rules_oci and rules_img, and rules_helm stamps the pushed repository and digest into the chart. rules_helm itself depends on neither. Each is wired up by a companion module that lives in this repository under extensions/ and is released from the same tag, with the same version, as rules_helm.

ModuleDepends onLoad from
rules_helm_imgrules_img@rules_helm_img//:defs.bzl
rules_helm_ocirules_oci@rules_helm_oci//:defs.bzl

As in rules_helm, each rule also has its own file next to defs.bzl, e.g. @rules_helm_img//:helm_img_image.bzl, for BUILD files that only want one thing.

Each module re-exports every public symbol of @rules_helm//helm:defs.bzl plus the push rule its image rules provide (image_push or oci_push), so a chart that bundles images is written against one load. Rules that are specific to one set of image rules land in its module rather than in rules_helm.

The contract

rules_helm reads one thing from an image: HelmImageInfo. It carries the label values refer to, a repository file, the raw manifest whose sha256 is the digest, the remote tags, and the executable that pushes the image. helm_package.images accepts any target that provides it.

Three things provide it today:

  • rules_helm itself, for oci_push, image_push and image_import targets listed directly in images. An aspect recognises them by shape and reads their attributes, which is all it can do without depending on either ruleset. This is what keeps existing charts working unchanged.
  • helm_img_image from rules_helm_img and helm_oci_image from rules_helm_oci. These read the image rules' own providers (DeployInfo and PullInfo in the case of rules_img) and are the preferred path for new charts. Values keep referring to the wrapped push target.
  • helm_image from rules_helm, which takes the files directly, for images built by something else entirely.

Setup

bazel_dep(name = "rules_helm_img", version = "{version}")

A bazel_dep on the companion module pulls in rules_helm, so it does not need to be listed separately. The rules for building the images themselves (image_manifest, oci_image and friends) are still loaded from rules_img or rules_oci, which means a direct bazel_dep on whichever one you use.

Example

load("@rules_helm_img//:defs.bzl", "helm_chart", "helm_img_image", "image_push")
load("@rules_img//img:image.bzl", "image_manifest")

image_manifest(
    name = "app",
    layers = [":app_layer"],
)

image_push(
    name = "app.push",
    image = ":app",
    registry = "docker.io",
    repository = "my-org/app",
    tags = ["latest"],
)

helm_img_image(
    name = "app.helm",
    image = ":app.push",
)

helm_chart(
    name = "chart",
    images = [":app.helm"],
)

With values.yaml referencing the push target by label:

image: "{@//:app.push}"

The packaged chart carries docker.io/my-org/app@sha256:... in its place.

Pushing the chart with multi_deploy

rules_img's multi_deploy pushes all of its operations in one run, but only targets that provide DeployInfo or MultipleDeployInfo can be operations, and helm_push provides neither. helm_oci_manifest from rules_helm_img describes the chart as the OCI artifact helm push creates, so the chart and its images can be pushed together:

load("@rules_helm_img//:defs.bzl", "helm_oci_manifest")
load("@rules_img//img:multi_deploy.bzl", "multi_deploy")

helm_oci_manifest(
    name = "chart.oci_manifest",
    chart = ":chart",
    registry_url = "oci://registry.example.com/charts",
)

multi_deploy(
    name = "deploy",
    operations = [
        ":app.push",
        ":chart.oci_manifest",
    ],
)

helm_oci_manifest

load("@rules_helm_img//:helm_oci_manifest.bzl", "helm_oci_manifest")

helm_oci_manifest(*, name, chart, registry_url, registry_url_file, visibility, **kwargs)

Describe a chart as the OCI artifact helm push creates, for rules_img's multi_deploy.

The target is an image_manifest that provides DeployInfo, so it can be listed in the operations of a multi_deploy. Running the multi_deploy pushes the chart to <registry_url>/<chart name>:<chart version>, with + in the version replaced by _, as helm push would. Only the chart is pushed; push its images with their own targets.

load("@rules_helm_img//:defs.bzl", "helm_oci_manifest")
load("@rules_img//img:multi_deploy.bzl", "multi_deploy")

helm_oci_manifest(
    name = "my_chart_oci_manifest",
    chart = ":my_chart",
    registry_url = "oci://registry.example.com/charts",
)

multi_deploy(
    name = "deploy",
    operations = [":my_chart_oci_manifest"],
)

The pushed manifest is the one helm push creates when it runs in UTC, so its digest is the one helm_oci_digest gives. Helm writes the org.opencontainers.image.created annotation in the local time zone, so helm push in another zone pushes a different digest for the same chart.

Compared with helm_push:

  • Only oci:// registries are supported, so push_cmd and plugins such as cm-push are not.
  • Registry credentials come from rules_img (Docker config and credential helpers), not from the HELM_REGISTRY_* variables (HELM_REGISTRY_USERNAME, HELM_REGISTRY_PASSWORD and HELM_REGISTRY_PASSWORD_FILE).
  • There is no include_images.

rules_img expands Go templates in annotation values. {{ in a chart's metadata is escaped, so the annotations match the chart.
